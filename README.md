# KalendarB24 REST: планирование отпусков для облачного Битрикс24

Тиражное серверное REST-приложение для Маркета Битрикс24. С коробочным модулем `kalendarb24.vacation` код не делит: нужная логика копируется, а не подключается.

На сервере не хранятся ФИО и другие данные сотрудников, только их ID в портале. Имена интерфейс берёт прямо в браузере через `BX24.callMethod('user.get')`.

Разработка идёт блоками MVP. Каждый блок проверяется на облачном портале, и только потом начинается следующий.

## Блок 1: каркас

- `/install` — путь для первоначальной установки. Портал присылает POST с `REFRESH_ID`. Сервер обновляет токен на `oauth.bitrix.info`, берёт `member_id`, домен и `client_endpoint` из ответа сервера авторизации (не из запроса) и сохраняет портал. Затем страница вызывает `BX24.installFinish()`.
- `/app` — путь обработчика: главная страница в iframe.
- `/api/me` — сервер проверяет токен пользователя из `BX24.getAuth()` вызовом `user.current` и `user.admin` на адрес портала из БД.
- `/api/check` — сервер вызывает `app.info` по сохранённому токену приложения и при необходимости обновляет токен.

## Блок 2: структура компании

- `/api/structure` — отделы из `department.get` (с `PARENT` и `UF_HEAD`), отделы сотрудника из `user.get` (только `ID` и `UF_DEPARTMENT`) и цепочка руководителей. Руководитель ищется как в коробке: руководитель своего отдела, а если это сам сотрудник или руководителя нет, то выше по дереву.
- `/api/hr-compare` — для сравнения: руководители из новой структуры через `humanresources.node.list` и `humanresources.node.get` (REST 3.0, адрес `/rest/api/`). Нужен, чтобы выбрать источник руководителей.

Права приложения: добавьте «Структура компании (department)» и, для сравнения, «humanresources». ФИО сервер не запрашивает, имена подставляет браузер.

## Блок 3: хранилище данных в портале

Данные приложения (заявки, история согласования) лежат в портале клиента, в хранилищах `entity.*`. На нашем сервере остаются только токены.

- При установке сервер создаёт хранилища `kbreq` (заявки) и `kbhist` (история) и их свойства. Сотрудник хранится как ID, без ФИО. Повторный запуск создаёт только недостающее.
- Права в `entity.add` не передаются, поэтому управление (X) есть только у администратора, установившего приложение. Сервер пишет его токеном, остальные сотрудники напрямую данные не читают и не меняют.
- `/api/storage` (администратор) — создаёт недостающее и показывает свойства и `entity.rights`.
- `/api/storage/probe` (POST) — пробная запись: добавить, изменить одно свойство, прочитать, удалить. Показывает, сохраняет ли `entity.item.update` непереданные свойства (в документации не сказано).

Права приложения: добавьте «Хранилище данных (entity)». Переустанавливать не нужно: токен, который сервер обновляет сам, сохраняет права на момент установки, поэтому при каждом открытии приложения тем, кто его устанавливал, сервер берёт свежие токены из запроса портала. Достаточно открыть приложение под этим администратором.

Важно: при удалении **локального** приложения портал всегда удаляет его данные, а новое локальное приложение получает новый `client_id`. У тиражного приложения данные сохраняются, если администратор не отметил «Удалить настройки и данные приложения» ([документация](https://apidocs.bitrix24.com/settings/app-uninstallation.html)).

## Блок 3, шаг 2: заявки и согласование

Логика перенесена из коробочного модуля без изменений: `src/Domain` (`DateRange`, `WorkingDays`, `ApprovalRoute`, `Status`) и их тесты.

- Сотрудник подаёт заявку: вид, даты. Сервер проверяет даты, пересечение со своими заявками и считает дни. Для ежегодного отпуска праздники из `calendar.settings.get` не считаются (ст. 120 ТК РФ), для остальных видов дни календарные.
- Маршрут по умолчанию как в коробке: руководитель → отдел кадров → директор. Руководитель берётся из структуры (`department.get`), если в отделе его нет, то выше по дереву. Заявку директора проверяет только ОК. Если ближайший руководитель и есть директор, второй раз он не утверждает. Из сотрудников ОК заявка достаётся тому, у кого меньше заявок на проверке, и не самому автору.
- Решение принимает только текущий согласующий. Причина отказа выбирается из списка, свободного текста нет. Обсудить заявку можно в чате Битрикс24: кнопка в карточке открывает диалог через `BX24.im.openMessenger`.
- Карточку видят автор, согласующие, директор, ОК и администратор портала.
- Роли (директор, ОК) задаёт администратор на вкладке «Настройки», они хранятся в хранилище `kbrole`. Сотрудника выбирают по структуре компании: отдел, затем сотрудник, или поиск по фамилии (`department.get`, `user.get` из браузера). Стандартный диалог `BX24.selectUser` не используется, на части тарифов он отвечает ACCESS_DENIED.
- Пока нет: настраиваемых маршрутов, заместителей, лимитов отделов и остатков (следующие блоки).

Права приложения: добавьте «Календарь (calendar)». Новые хранилища и свойства сервер создаёт сам, когда приложение открывает установивший его администратор.

## Блок 4: уведомления

Сервер присылает системные уведомления Битрикс24 ([`im.notify.system.add`](https://apidocs.bitrix24.com/api-reference/chats/notifications/im-notify-system-add.html)):

| Событие | Кому |
|---|---|
| заявка подана или перешла на следующий шаг | согласующему, от которого теперь ждут решения |
| заявка согласована на шаге | автору: у кого она теперь |
| заявка утверждена | автору |
| заявка отклонена | автору (с причиной) и тем, кто уже согласовал |
| заявка отозвана | текущему согласующему и тем, кто уже согласовал |

- В уведомлении ссылка «Открыть заявку № …» вида `/marketplace/view/<код приложения>/?params[req]=<ID>`. Портал открывает приложение в слайдере через встройку [`REST_APP_URI`](https://apidocs.bitrix24.com/api-reference/widgets/universal/app-url.html), и приложение сразу показывает карточку. Обработчик встройки (`<APP_URL>/app`) сервер регистрирует сам при установке и когда приложение открывает установивший его администратор; после смены адреса туннеля он перерегистрируется.
- Код приложения в ссылке у локального приложения равен `B24_CLIENT_ID`, у приложения из Маркета он другой, его задаёт `APP_CODE`.
- Уведомления уходят одним вызовом `batch` уже после ответа браузеру, поэтому действие не становится медленнее. Ошибка отправки не отменяет действие, она пишется в лог контейнера.
- Для текста «Фамилия Имя просит согласовать» сервер запрашивает ФИО автора через `user.get` и нигде его не сохраняет.
- Тому, кто сам сделал действие, уведомление не приходит. При `ALLOW_SELF_APPROVAL=1` (проверка под одним аккаунтом) приходит, иначе проверить уведомления в одиночку нельзя.
- Новое уведомление по той же заявке заменяет у получателя прежнее (`TAG`).

Права приложения: добавьте «Чаты и уведомления (im)» и «Встраивание приложений (placement)», затем откройте приложение под администратором, который его устанавливал: сервер возьмёт токены с новыми правами и зарегистрирует обработчик ссылок.

## Блок 5: событие в календаре

- Когда заявку утверждают окончательно, сервер после ответа браузеру создаёт в календаре автора событие на весь период: [`calendar.event.add`](https://apidocs.bitrix24.com/api-reference/calendar/calendar-event/calendar-event-add.html) с `type=user`, `ownerId` автора, `skip_time=Y`, `accessibility=absent` («Отсутствую»), название — вид отпуска. Секцию календаря портал выбирает сам.
- Событие пишется токеном приложения, то есть от имени администратора, установившего приложение. Без явного календаря портал ответил «Доступ запрещен», поэтому сервер берёт календарь сотрудника, в который ему можно добавлять события (`calendar.section.get`, флаг `PERM.add`), а если такого нет, создаёт сотруднику календарь «Отпуска» (`calendar.section.add`: администратор может создавать календари другим пользователям). Результат сохраняется в заявке (`CAL_EVENT_ID` или текст ошибки в `CAL_ERROR`) и показывается в карточке, автор или администратор может нажать «Добавить событие ещё раз».
- По [справке](https://helpdesk.bitrix24.ru/open/5257065/) событие со статусом «Отсутствую» попадает в график отсутствий.
- Ошибка календаря не отменяет утверждение.
- Отмена утверждённой заявки, как в коробке: автор отменяет не позже чем за N рабочих дней до начала (по умолчанию 3, меняется на вкладке «Настройки», хранится в `app.option`) и указывает причину. Отмену согласует руководитель, затем сотрудник ОК (с наименьшей загрузкой, не автор), любой из них может отказать с причиной. После согласования заявка «Отменена», событие удаляется (`calendar.event.delete`), участники получают уведомление. При отказе заявка снова «Утверждена».
- Шага бухгалтерии (в коробке — если отпуск уже оплачен) пока нет: появится вместе с ролью бухгалтерии.

Права приложения: новых нет. `calendar` добавлен в блоке 3, `app.option` входит в базовые права.

## Запуск на Windows (localhost)

Нужны Docker Desktop и [mkcert](https://github.com/FiloSottile/mkcert). Портал требует HTTPS, а самоподписанный сертификат mkcert добавляет в доверенные.

1. Склонируйте репозиторий, например, в `E:\VibeCoding\KalendarB24-REST`.
2. Выпустите сертификат для localhost:
   ```
   mkcert -install
   mkcert -cert-file docker\certs\localhost.pem -key-file docker\certs\localhost-key.pem localhost 127.0.0.1
   ```
3. Скопируйте `.env.example` в `.env`.
4. На тестовом облачном портале откройте «Разработчикам → Другое → Локальное приложение»:
   - тип: серверное, с интерфейсом;
   - путь вашего обработчика: `https://localhost:8443/app`;
   - путь для первоначальной установки: `https://localhost:8443/install`;
   - права: `user` (`basic` выдаётся всегда), `department`, `humanresources`, `entity`, `calendar`, `im`, `placement`.

   Сохраните и впишите «Код приложения» и «Ключ приложения» в `B24_CLIENT_ID` и `B24_CLIENT_SECRET` в `.env`.
5. Запустите:
   ```
   docker compose up -d --build
   docker compose exec app composer install
   ```
   Порт 8443 выбран, чтобы не пересекаться с env-docker коробки (80/443). Таблицы создаются сами при первом запросе.
6. Откройте https://localhost:8443/app в браузере один раз, чтобы убедиться, что сертификат принят. Затем откройте приложение на портале. Установка запустится сама, после неё появится таблица проверок.

## Что проверяем в блоке 1

| Проверка | Ожидаемо |
|---|---|
| BX24.init | домен и member_id портала |
| user.current в браузере | ваш ID и ФИО (только в браузере) |
| /api/me | ваш ID и признак администратора, определённые сервером |
| /api/check | `app.info`: CODE, STATUS = L, INSTALLED = true |

## Скрипты для Windows

В папке `scripts` (запускать двойным щелчком):

| Скрипт | Что делает |
|---|---|
| `start-rest.cmd` | запускает Docker Desktop при необходимости, поднимает туннель Cloudflare, записывает его адрес в `APP_URL`, запускает контейнеры, проверяет, что приложение отвечает через туннель, и показывает оба пути для настроек локального приложения (путь обработчика копирует в буфер обмена) |
| `stop-rest.cmd` | закрывает туннель и останавливает контейнеры, база сохраняется |
| `sync-git.cmd` | забирает изменения из GitHub для `E:\VibeCoding\KalendarB24` и `E:\VibeCoding\KalendarB24-REST`, пропускает папку с несохранёнными правками и показывает ветки от Claude |

Коробку (env-docker) эти скрипты не трогают, для неё есть отдельные `start-box.cmd` и `stop-box.cmd`.

## Публичный адрес через туннель

Форма локального приложения не принимает `https://localhost`: по [документации](https://apidocs.bitrix24.ru/local-integrations/serverside-local-app-with-ui.html) адрес обработчика должен быть доступен из внешней сети. Поэтому приложение по-прежнему работает в Docker на вашем компьютере, а наружу его открывает туннель: сервис выдаёт публичный https-адрес и пересылает запросы на `http://localhost:8080`.

1. Запустите туннель на порт 8080 и получите публичный адрес, например `https://abc123.example-tunnel.ru`.
2. В форме приложения укажите `https://<адрес туннеля>/app` и `https://<адрес туннеля>/install`.
3. Пропишите тот же адрес в `APP_URL` в `.env`.

Бесплатный адрес туннеля обычно меняется при каждом запуске, тогда пути в форме приложения придётся обновлять. С туннелем портал сможет присылать и события (`ONAPPINSTALL`, `ONAPPUNINSTALL`), они понадобятся в следующих блоках.
