# KalendarB24 REST: планирование отпусков для облачного Битрикс24

Тиражное серверное REST-приложение для Маркета Битрикс24. С коробочным модулем `kalendarb24.vacation` код не делит: нужная логика копируется, а не подключается.

На сервере не хранятся ФИО и другие данные сотрудников, только их ID в портале. Имена интерфейс берёт прямо в браузере через `BX24.callMethod('user.get')`.

Разработка идёт блоками MVP. Каждый блок проверяется на облачном портале, и только потом начинается следующий.

## Блок 1: каркас

- `/install` — путь для первоначальной установки. Портал присылает POST с `REFRESH_ID`. Сервер обновляет токен на `oauth.bitrix.info`, берёт `member_id`, домен и `client_endpoint` из ответа сервера авторизации (не из запроса) и сохраняет портал. Затем страница вызывает `BX24.installFinish()`.
- `/app` — путь обработчика: главная страница в iframe.
- `/api/me` — сервер проверяет токен пользователя из `BX24.getAuth()` вызовом `user.current` и `user.admin` на адрес портала из БД.

## Блок 2: структура компании

- Отделы берутся из `department.get` (с `PARENT` и `UF_HEAD`), отделы сотрудника из `user.get` (только `ID` и `UF_DEPARTMENT`). Руководитель ищется как в коробке: руководитель своего отдела, а если это сам сотрудник или руководителя нет, то выше по дереву.

Права приложения: «Структура компании (department)». ФИО сервер не запрашивает, имена подставляет браузер.

## Блок 3: хранилище данных в портале

Данные приложения (заявки, история согласования) лежат в портале клиента, в хранилищах `entity.*`. На нашем сервере остаются только токены.

- При установке сервер создаёт хранилища `kbreq` (заявки) и `kbhist` (история) и их свойства. Сотрудник хранится как ID, без ФИО. Повторный запуск создаёт только недостающее.
- Права в `entity.add` не передаются, поэтому управление (X) есть только у администратора, установившего приложение. Сервер пишет его токеном, остальные сотрудники напрямую данные не читают и не меняют.
- `/api/storage` (администратор) — создаёт недостающее и показывает свойства и `entity.rights`.

Права приложения: добавьте «Хранилище данных (entity)». Переустанавливать не нужно: токен, который сервер обновляет сам, сохраняет права на момент установки, поэтому при каждом открытии приложения тем, кто его устанавливал, сервер берёт свежие токены из запроса портала. Достаточно открыть приложение под этим администратором.

Важно: при удалении **локального** приложения портал всегда удаляет его данные, а новое локальное приложение получает новый `client_id`. У тиражного приложения данные сохраняются, если администратор не отметил «Удалить настройки и данные приложения» ([документация](https://apidocs.bitrix24.com/settings/app-uninstallation.html)).

## Блок 3, шаг 2: заявки и согласование

Логика перенесена из коробочного модуля без изменений: `src/Domain` (`DateRange`, `WorkingDays`, `ApprovalRoute`, `Status`) и их тесты.

- Сотрудник подаёт заявку: вид, даты. Сервер проверяет даты, пересечение со своими заявками и считает дни. Для ежегодного отпуска праздники из `calendar.settings.get` не считаются (ст. 120 ТК РФ), для остальных видов дни календарные.
- Маршрут по умолчанию как в коробке: руководитель → отдел кадров → директор. Руководитель берётся из структуры (`department.get`), если в отделе его нет, то выше по дереву. Заявку директора проверяет только ОК. Если ближайший руководитель и есть директор, второй раз он не утверждает. Из сотрудников ОК заявка достаётся тому, у кого меньше заявок на проверке, и не самому автору; если автор — единственный сотрудник ОК, шаг ОК проходит его непосредственный руководитель (без руководителя — директор). Так же при отмене.
- Одну заявку никто не согласует дважды: если согласующий следующего шага уже согласовал эту заявку (например, руководитель проверяет её и за ОК), шаг засчитывается автоматически и отмечается в истории. Так же при отмене.
- Решение принимает только текущий согласующий. Причина отказа выбирается из списка, свободного текста нет. Обсудить заявку можно в чате Битрикс24: кнопка в карточке открывает диалог через `BX24.im.openMessenger`.
- Карточку видят её участники (автор, согласующие, получатели результата), руководитель отдела и те, чьи роли на вкладке «Доступ» открывают заявки этого отдела.
- Роли задаются на вкладке «Доступ» (см. ниже). Сотрудника выбирают по структуре компании: отдел, затем сотрудник, или поиск по фамилии (`department.get`, `user.get` из браузера). Стандартный диалог `BX24.selectUser` не используется, на части тарифов он отвечает ACCESS_DENIED.
- Пока нет: настраиваемых маршрутов, заместителей, лимитов отделов и остатков (следующие блоки).

Права приложения: добавьте «Календарь (calendar)». Новые хранилища и свойства сервер создаёт сам, когда приложение открывает установивший его администратор.

## Блок 4: уведомления

Сервер присылает системные уведомления Битрикс24 ([`im.notify.system.add`](https://apidocs.bitrix24.com/api-reference/chats/notifications/im-notify-system-add.html)):

| Событие | Кому |
|---|---|
| заявка подана или перешла на следующий шаг | согласующему, от которого теперь ждут решения |
| заявка согласована на шаге | автору: у кого она теперь |
| заявка утверждена | автору |
| заявка отклонена | автору (с причиной) и тем, кто уже согласовал |
| заявка отозвана | текущему согласующему и тем, кто уже согласовал |

- В уведомлении ссылка «Открыть заявку № …» вида `/marketplace/view/<код приложения>/?params[req]=<ID>`. Портал открывает приложение в слайдере через встройку [`REST_APP_URI`](https://apidocs.bitrix24.com/api-reference/widgets/universal/app-url.html), и приложение сразу показывает карточку. Обработчик встройки (`<APP_URL>/app`) сервер регистрирует сам при установке и когда приложение открывает установивший его администратор; после смены адреса туннеля он перерегистрируется.
- Код приложения в ссылке у локального приложения равен `B24_CLIENT_ID`, у приложения из Маркета он другой, его задаёт `APP_CODE`.
- Уведомления уходят одним вызовом `batch` уже после ответа браузеру, поэтому действие не становится медленнее. Ошибка отправки не отменяет действие, она пишется в лог контейнера.
- Для текста «Фамилия Имя просит согласовать» сервер запрашивает ФИО автора через `user.get` и нигде его не сохраняет.
- Тому, кто сам сделал действие, уведомление не приходит. При `ALLOW_SELF_APPROVAL=1` (проверка под одним аккаунтом) приходит, иначе проверить уведомления в одиночку нельзя.
- Новое уведомление по той же заявке заменяет у получателя прежнее (`TAG`).

Права приложения: добавьте «Чаты и уведомления (im)» и «Встраивание приложений (placement)», затем откройте приложение под администратором, который его устанавливал: сервер возьмёт токены с новыми правами и зарегистрирует обработчик ссылок.

## Блок 5: график отсутствий и календарь

- Когда заявку утверждают окончательно, сервер после ответа браузеру делает то же, что коробка: запись в «График отсутствий» и событие в календаре сотрудника. Результат сохраняется в заявке (`ABSENCE_ID`, `CAL_EVENT_ID`, текст ошибки в `CAL_ERROR`) и показывается в карточке. Автор или администратор может нажать «Добавить в график и календарь»: создаётся только то, чего ещё нет. Ошибка не отменяет утверждение.
- График отсутствий — инфоблок `absence` типа `structure`. Общий список инфоблоков этого типа (`lists.get` без кода) портал не отдаёт (ACCESS_DENIED), а по `IBLOCK_CODE=absence` чтение и запись работают (проверено на портале). Свойства сотрудника и типа ищутся по коду (`USER`, `ABSENCE_TYPE`) через `lists.field.get`. Значения типа REST отдаёт без XML_ID, поэтому тип выбирается по названию: «отпуск ежегодный», «отгул за свой счет» (без сохранения заработной платы), иначе «другое». Запись: [`lists.element.add`](https://apidocs.bitrix24.com/api-reference/lists/elements/lists-element-add.html) с `ELEMENT_CODE=kb24_req_<ID>`, даты в формате ДД.ММ.ГГГГ.
- Событие: [`calendar.event.add`](https://apidocs.bitrix24.com/api-reference/calendar/calendar-event/calendar-event-add.html) с `type=user`, `ownerId` автора, `skip_time=Y`, название — вид отпуска. Пишется токеном приложения, то есть от имени администратора, установившего приложение. Без явного календаря портал ответил «Доступ запрещен», поэтому сервер берёт календарь «Отпуска», созданный им раньше, или календарь сотрудника с `PERM.add`, а если такого нет, создаёт календарь «Отпуска» (`calendar.section.add`).
- Событие ставится «Занят» (`accessibility=busy`), а не «Отсутствую». Проверка на портале показала, что график отсутствий показывает события «Отсутствую» по создателю, то есть у администратора, а не у сотрудника. Поэтому в графике остаётся только запись сотрудника.
- Отмена утверждённой заявки, как в коробке: автор отменяет не позже чем за N рабочих дней до начала (срок задаёт маршрут отзыва; если не задан или маршрут не подошёл — значение из вкладки «Настройки», по умолчанию 3, хранится в `app.option`) и указывает причину. Отмену согласуют шаги маршрута отзыва (см. «Маршруты отзыва»), любой из согласующих может отказать с причиной. После согласования заявка «Отменена», запись в графике и событие удаляются (`lists.element.delete`, `calendar.event.delete`), участники получают уведомление. При отказе заявка снова «Утверждена».
- Шага бухгалтерии (в коробке — если отпуск уже оплачен) пока нет: появится вместе с ролью бухгалтерии.

Права приложения: добавлено «Списки» (`lists`). `calendar` добавлен в блоке 3, `app.option` входит в базовые права.

## Блок 6: календарь отдела и лимиты

- Вкладка «Календарь» открывается первой, как в коробке: месяц, квартал или год, фильтр по сотруднику. Цвет показывает вид отсутствия, заливка статус (контур у руководителя, штриховка в ОК или у директора, сплошная утверждено). По клику на день видно, кто отсутствует, и можно подать заявку с этой даты.
- Какие отделы видны в календаре, задают роли на вкладке «Доступ»: свой отдел, с подотделами или вся компания. Руководитель видит и отделы, которыми руководит.
- Лимиты отделов задаёт администратор в настройках (хранилище `kblimit`): максимум отсутствующих в один день и максимум дней пересечения двух отсутствий, с подотделами или без, с руководителем или без. Пустое поле значит «без ограничения». Лимит проверяется при подаче заявки; дни, когда лимит исчерпан, в календаре красные.
- Заявки относятся к отделу, в котором сотрудник был при подаче (`DEPT_ID`): сервер не запрашивает всех сотрудников отдела. Сотрудников отдела и их ФИО для календаря запрашивает браузер через `user.get`.
- В сообщении о пересечении сервер пишет коллегу как `{user:ID}`, имя подставляет браузер.

## Блок 7: остатки отпуска

- Вкладка «Остатки», как в коробке: открывается ролям с доступом к ней, вносить остаток ежегодного отпуска на дату и дату приёма могут роли с правом изменения. Одна запись на сотрудника в хранилище `kbbal`, сотрудник указан только ID.
- В каждую годовщину приёма после даты остатка добавляется норма из настроек (`annual_days`, от 28 до 100, по умолчанию 28). Действующие заявки на ежегодный отпуск с началом не раньше даты остатка его уменьшают. Без внесённого остатка ограничения нет.
- При подаче заявки на ежегодный отпуск проверяется остаток к дате начала (с годовщинами до неё). В форме заявки видно, сколько доступно.
- CSV как в коробке: «Скачать шаблон» выгружает сотрудников выбранного отдела с текущими данными, «Загрузить CSV» принимает тот же файл (разделитель «;», «,» или табуляция; даты 31.12.2026 или 31.12.26; кодировка UTF-8, Windows-1251 или UTF-16, как сохраняют Excel и Calc). Файл разбирает браузер, он же находит сотрудника по ФИО, если нет ID, и отправляет только изменённые строки (до 1000 за раз).
- Список сотрудников, ФИО и отделы браузер берёт через `user.get` (`ACTIVE`, `USER_TYPE=employee`).

## Блок 8: маршруты согласования

- Вкладка «Маршруты» для администратора и сотрудников, которых он добавил в список «Кто настраивает маршруты» (роль `route_editor` в `kbrole`). Маршрут — одна запись `kbroute`, шаги в ней одним JSON (до 10 шагов). У шага постоянный номер внутри маршрута, по нему уже поданные заявки узнают, что шаг выключили.
- Маршрут задаёт виды отсутствия и отделы (пусто — все; подотделы входят). Срабатывает самый точный: закреплённый за видом как единственный вариант, затем маршрут ближайшего отдела с видом, отдела без вида, вида без отдела, общий. Не подошёл ни один — маршрут «По умолчанию» (руководитель, ОК, директор). Он настраивается так же, как остальные, но действует на все виды и отделы и не выключается; пока его не сохраняли, он не хранится в портале (`IS_DEFAULT=Y` после сохранения). Его можно удалить, если есть другие маршруты согласования (признак `default_route_removed` в `app.option`): тогда заявка, которой не подошёл ни один маршрут, утверждается сразу. Так же сразу утверждается заявка, если у маршрута выключены все шаги или согласовать её может только сам автор (например, директор): в истории запись «Согласующих нет: утверждено сразу». Заявки, поданные до этого обновления, доходят по прежней цепочке.
- Шаг: название, кто согласует (руководитель по структуре, роль с вкладки «Доступ» по очереди или конкретный сотрудник), до какого срока может отклонить, за сколько дней до начала подавать заявку. Срок подачи задаётся в шагах, прежняя настройка `min_submit_days` стала начальным сроком маршрута «По умолчанию». В настройках можно освободить от срока отпуск без сохранения (`min_submit_exempt_unpaid`).
- Шаг пропускается, если согласующий — автор заявки (кроме режима `ALLOW_SELF_APPROVAL=1`) или уже согласовал её раньше; шаг ОК — если заявку уже согласовал любой сотрудник ОК. Если согласующего на шаге нет, заявка уходит в ОК, это видно в истории. Выключенный шаг пропускается и в поданных заявках.
- Заявка хранит снимок маршрута на момент подачи (`ROUTE_DATA`) и номер текущего шага (`STEP`), статус `route_review`. В карточке видны шаги: ✓ согласовано, ● сейчас здесь, ○ впереди, – пропущен, ✕ отклонено.
- «Уведомить о результате» в маршруте: кого уведомить (роль или сотрудник), о чём (утверждение, отмена утверждённого), задача («не ставить», «ставить сразу», «спросить при ознакомлении») и её срок за N дней до начала. В уведомление Битрикс24 кнопки не добавить, поэтому в нём ссылка на карточку заявки, а в карточке кнопка «Ознакомился» и, при режиме «спросить», выбор задачи и срока. Записи ознакомления — хранилище `kback`. Заявки, с которыми нужно ознакомиться, видны и на вкладке «На согласовании».
- Задача ставится методом `tasks.task.add`: ответственный — получатель, постановщик — автор заявки, срок до 18:00 выбранного дня. Права приложения: добавьте «Задачи» (`task`) и откройте приложение под администратором, который его устанавливал.
- Напоминания: тем, кто не ознакомился, каждый рабочий день (по настройкам рабочего времени портала) до начала отсутствия. Битрикс24 не вызывает приложение по расписанию, поэтому напоминания рассылает `php bin/remind.php`: на рабочем сервере — cron раз в день, например `0 9 * * * cd /путь/к/приложению && php bin/remind.php` (в Docker: `docker compose exec -T app php bin/remind.php`). На тестовом сервере скрипт запускают вручную, когда нужно проверить напоминания: `scripts\remind.cmd`. Повторный запуск в тот же день ничего не шлёт.
- Вкладка «На ознакомлении» со счётчиком: заявки, с результатом которых сотрудник ещё не ознакомился.

## Запуск на Windows (localhost)

Нужны Docker Desktop и [mkcert](https://github.com/FiloSottile/mkcert). Портал требует HTTPS, а самоподписанный сертификат mkcert добавляет в доверенные.

1. Склонируйте репозиторий, например, в `E:\VibeCoding\KalendarB24-REST`.
2. Выпустите сертификат для localhost:
   ```
   mkcert -install
   mkcert -cert-file docker\certs\localhost.pem -key-file docker\certs\localhost-key.pem localhost 127.0.0.1
   ```
3. Скопируйте `.env.example` в `.env`.
4. На тестовом облачном портале откройте «Разработчикам → Другое → Локальное приложение»:
   - тип: серверное, с интерфейсом;
   - путь вашего обработчика: `https://localhost:8443/app`;
   - путь для первоначальной установки: `https://localhost:8443/install`;
   - права: `user` (`basic` выдаётся всегда), `department`, `humanresources`, `entity`, `calendar`, `im`, `placement`.

   Сохраните и впишите «Код приложения» и «Ключ приложения» в `B24_CLIENT_ID` и `B24_CLIENT_SECRET` в `.env`.
5. Запустите:
   ```
   docker compose up -d --build
   docker compose exec app composer install
   ```
   Порт 8443 выбран, чтобы не пересекаться с env-docker коробки (80/443). Таблицы создаются сами при первом запросе.
6. Откройте https://localhost:8443/app в браузере один раз, чтобы убедиться, что сертификат принят. Затем откройте приложение на портале. Установка запустится сама, после неё откроется календарь.

## Развёртывание на виртуальном хостинге (hoster.by)

Сервер должен работать постоянно: портал обращается к нему при каждом открытии приложения, а cron рассылает напоминания. Docker не нужен: настройки берутся из файла `.env` в корне приложения (переменные окружения, если они заданы, важнее файла).

Нужно: поддомен с HTTPS, PHP 8.3+ (проверено с 8.3, на хостинге 8.5) с расширениями `pdo_mysql`, `curl`, `mbstring`, база MySQL, SSH и cron. Названия пунктов панели управления ниже общие: сверяйте с панелью hoster.by.

1. **Поддомен**, например `vacation.aplat.by`. Корень сайта — папка `public` приложения. Если корень нельзя указать, корнем делают папку приложения: корневой `.htaccess` закрывает служебные файлы (`.env`, `src`, `vendor` и др.) и отдаёт всё из `public`.
2. **SSL** для поддомена (Let's Encrypt в панели). Приложение должно открываться по `https://` без предупреждений браузера.
3. **PHP** для поддомена — 8.3 или новее. Лучше PHP-FPM или LiteSpeed (LSAPI): тогда уведомления уходят уже после ответа браузеру (`fastcgi_finish_request` / `litespeed_finish_request`); в другом режиме всё работает, но действие отвечает на долю секунды медленнее.
4. **База MySQL** и пользователь с полными правами на неё. Таблицы создаются сами при первом запросе.
5. **Код** по SSH:
   ```
   git clone https://github.com/PlatonOriginal/kalendarb24-rest.git ~/vacation
   cd ~/vacation
   composer install --no-dev --optimize-autoloader
   ```
   Если `composer` на хостинге нет: `php -r "copy('https://getcomposer.org/installer','setup.php');" && php setup.php && php composer.phar install --no-dev --optimize-autoloader`. Без SSH можно выполнить `composer install` у себя и залить папку целиком, вместе с `vendor`.
6. **`.env`**: скопируйте `.env.example` в `.env` и заполните `B24_CLIENT_ID`, `B24_CLIENT_SECRET`, `APP_URL=https://vacation.aplat.by`, `DB_HOST` (обычно `localhost`), `DB_NAME`, `DB_USER`, `DB_PASSWORD`. Права только для владельца: `chmod 600 .env`.
7. **Cron** раз в день (путь к PHP смотрите в панели, у разных версий он разный):
   ```
   0 9 * * * cd ~/vacation && php bin/remind.php >> ~/vacation-remind.log 2>&1
   ```
8. **Портал**: в локальном приложении (или в карточке версии в Маркете) укажите `https://vacation.aplat.by/app` и `https://vacation.aplat.by/install`.
9. **Проверка**: `curl -I https://vacation.aplat.by/app` отвечает без ошибки сертификата; приложение открывается на портале.

Обновление вручную: `cd ~/vacation && git pull && composer install --no-dev --optimize-autoloader`.

На hoster.by то же одной командой: `sh ~/aplat.by/vacation/bin/update.sh` — забирает новые коммиты `main` и пересобирает автозагрузку; без новых коммитов пишет «Обновлений нет». Пути к PHP и composer меняются переменными `PHP` и `COMPOSER` (по умолчанию `/usr/local/bin/php` и `~/composer.phar`).

## Публичный адрес через туннель

Форма локального приложения не принимает `https://localhost`: по [документации](https://apidocs.bitrix24.ru/local-integrations/serverside-local-app-with-ui.html) адрес обработчика должен быть доступен из внешней сети. Поэтому приложение по-прежнему работает в Docker на вашем компьютере, а наружу его открывает туннель: сервис выдаёт публичный https-адрес и пересылает запросы на `http://localhost:8080`.

1. Запустите туннель на порт 8080 и получите публичный адрес, например `https://abc123.example-tunnel.ru`.
2. В форме приложения укажите `https://<адрес туннеля>/app` и `https://<адрес туннеля>/install`.
3. Пропишите тот же адрес в `APP_URL` в `.env`.

Бесплатный адрес туннеля обычно меняется при каждом запуске, тогда пути в форме приложения придётся обновлять. С туннелем портал присылает и события на `/event` (см. «Удаление приложения»).

## Удаление приложения

Сервер хранит о портале только адрес, токены приложения, кэш проверки токенов сотрудников и журнал запросов к REST за 3 суток (таблицы `portal`, `user_session` и `rest_log`). Когда приложение удаляют с портала, сервер стирает эти записи сам.

- При установке и при каждом изменении настройки (новая версия хранилищ, смена `APP_URL`) сервер вызывает `event.get` и подписывается через `event.bind` на `ONAPPUPDATE` и `ONAPPUNINSTALL` с обработчиком `APP_URL/event`. Обработчики со старым адресом снимает `event.unbind`. Нужен заданный `APP_URL`.
- `ONAPPUPDATE`: сервер проверяет пришедший `access_token` вызовом `app.info` по адресу портала из БД и сохраняет новый `application_token` ([безопасные обработчики](https://apidocs.bitrix24.ru/api-reference/events/safe-event-handlers.html)).
- `ONAPPUNINSTALL`: токенов доступа в событии нет, поэтому подлинность проверяется по сохранённому `application_token`. Если токена ещё нет (портал не присылал `ONAPPUPDATE`) или он не совпал, сервер вызывает `app.info` сохранёнными токенами: при удалении портал отзывает права приложения, и только ошибка авторизации подтверждает удаление. Если приложение отвечает, запрос отклоняется с 403, при ошибке сети данные не удаляются.
- Удаляются записи портала в `portal`, `user_session` и `rest_log`, независимо от флажка «Удалить настройки и данные приложения» (`data[CLEAN]`). Заявки, история и настройки хранятся в самом портале (`entity.*`, `app.option`), их удаляет портал по этому флажку.
- Порталы, установившие приложение раньше, подпишутся на события, когда администратор, установивший приложение, откроет его.

## Журнал запросов к REST

Каждый запрос сервера к REST API Битрикс24 (`/rest/`, `/rest/api/` и обновление токенов на `oauth.bitrix.info`) пишется в таблицу `rest_log`: время, `member_id` портала, метод, чей токен (`app` — приложения, `user` — сотрудника, открывшего приложение), HTTP-код, код ошибки из ответа и длительность в мс. Ошибка сети записывается с кодом 0.

- Параметры запросов, ответы, токены и `client_secret` в журнал не попадают: по записи видно, что вызывали и чем закончилось, но не какие данные передавались.
- Записи хранятся 3 суток (`RestLog::RETENTION`). Устаревшие удаляются после ответа браузеру в каждом запросе, где что-то записано в журнал, и ещё раз в `php bin/remind.php` по cron.
- При удалении приложения с портала журнал этого портала удаляется вместе с его записью в `portal`.
- Вызовы `BX24.callMethod` из браузера идут напрямую в портал, минуя сервер, поэтому в журнал не попадают.
- Сбой записи в журнал не ломает запрос к порталу: ошибка уходит в `error_log`.

Посмотреть журнал портала: `SELECT FROM_UNIXTIME(created_at), method, auth_type, http_status, error_code, duration_ms FROM rest_log WHERE member_id = '...' ORDER BY id DESC LIMIT 100`.

## Доступ

- Вкладка «Доступ»: роли с произвольными названиями, хранилище `kbaccess`. Роли правятся прямо в списке: карточка роли с составом и правами в сетке, у каждой своя кнопка «Сохранить». В роль входят сотрудники и отделы (с подотделами, участники отдела берутся через `user.get` с фильтром `UF_DEPARTMENT`).
- Роль открывает вкладки «Календарь», «Остатки», «Маршруты», «Настройки», «Доступ» (скрыта, просмотр или изменение) и задаёт, заявки каких отделов видны в календаре и в карточках: свой отдел, с подотделами или вся компания. «Мои заявки», «На согласовании» и «На ознакомлении» открыты всем. Вкладки «Дашборд» и «Дашборд: скорость согласования» — только скрыта или просмотр.
- Что можно сделать с заявкой, определяет участие в ней (автор, согласующий, получатель результата), а не роль. Руководитель видит заявки отделов, которыми руководит, с подотделами.
- Роль «Сотрудник» есть у всех. Если сотрудник в нескольких ролях, по каждой вкладке и по видимости берётся более широкое право. Администратор портала может всё. Кроме администратора, никто не может лишить себя права изменять «Доступ».
- При первом открытии после обновления прежние роли из `kbrole` переносятся в обычные роли «Директор», «Отдел кадров» и, если был список, «Настройка маршрутов» с прежними правами; прежняя настройка «Сотрудники видят календарь других отделов» переходит в видимость роли «Сотрудник». Это демо-данные для маршрута «По умолчанию»: роли можно переименовать и изменить.
- Шаг маршрута «Роль»: заявка достаётся участнику роли с наименьшим числом заявок на проверке, не самому автору; если в роли только автор, шаг засчитывается. Получатели результата из роли — все её участники. Роль, указанную в маршрутах, удалить нельзя. Шаги «Отдел кадров» и «Директор» из прежних маршрутов при чтении становятся шагами с перенесёнными ролями.
- Перенесённые роли «Директор» и «Отдел кадров» можно удалить, если их нет в маршрутах согласования и отзыва.

## Дашборд

- Как в коробке, за выбранный год: кто уже отдыхал, у кого отпуск только запланирован, кто не подал заявку и у кого нет части отпуска от 14 дней (ст. 125 ТК РФ); нагрузка по месяцам по всем доступным отделам и тепловая карта по отделам; скорость согласования по шагам маршрутов и согласующим, очередь ждущих решения.
- Вкладку открывает право «Дашборд» в роли, раздел о скорости согласования — право «Дашборд: скорость согласования». При переносе прежних ролей «Директор» получает оба права, «Отдел кадров» — только «Дашборд».
- Отделы на дашборде — те же, что видны по ролям в календаре и карточках. Нажатие на ячейку тепловой карты открывает календарь отдела на этот месяц, если отдел виден в календаре.
- «Больничные» и «Отгулы»: по утверждённым заявкам, дни внутри года и число случаев, по сотрудникам или по отделам (дни на человека). Прогулов в приложении пока нет.
- Сервер отдаёт только ID сотрудников, ФИО подставляет браузер.

## Маршруты отзыва

- На вкладке «Маршруты» отдельный раздел: кто согласует отмену утверждённого отсутствия. Записи `kbroute` с `PURPOSE=cancel`, шаги те же (руководитель, роль, сотрудник), без сроков подачи и отклонения. Срок отмены задаётся маршруту целиком («Отменить не позже чем за N раб. дн.», `CANCEL_DAYS`); пустое поле — срок из вкладки «Настройки».
- Маршрут выбирается по тем же правилам, что маршрут согласования (виды, отделы, «единственный вариант»), шаги пропускаются так же. Маршрута «По умолчанию» нет: если не подошёл ни один или согласовать может только сам сотрудник, отсутствие отменяется сразу и удаляется из графика и календаря, уведомление получают те, кто согласовал заявку.
- Снимок маршрута на момент запроса отмены — в `kbreq.CANCEL_DATA`, текущий шаг — `CANCEL_INDEX`. Отмены, начатые до обновления, доходят по прежней цепочке «руководитель → Отдел кадров».
- Отказ в отмене оставляет отсутствие утверждённым.
- «Уведомить об отмене» настраивается в маршруте отзыва, «Уведомить об утверждении» — в маршруте согласования.
- При первом открытии после обновления создаётся демо-маршрут «Отзыв по умолчанию» (руководитель → роль «Отдел кадров»), его можно изменить или удалить. Получатели события «отменено» из маршрутов согласования переносятся: из «По умолчанию» в демо-маршрут, из остальных — в маршруты «Отзыв: <название>» с теми же видами и отделами. Признак переноса — `cancel_routes_ready` в `app.option`.

## Больничный и отгул

- Виды «Отгул» (в днях, остаток не уменьшает, в лимит отдела входит) и «Больничный» (остаток не уменьшает, в лимит не входит, может приходиться на отпуск, вносится задним числом и без срока подачи).
- Право «Подача заявок за сотрудников» на вкладке «Доступ» добавляет в форму заявки поле «Сотрудник»: например, отдел кадров вносит больничный за заболевшего или фиксирует отгул. Выбрать можно сотрудника из отделов, видных по роли. Сотрудник получает уведомление, заявка видна в «Моих заявках» у обоих, отозвать её до решения может любой из них. У перенесённой роли «Отдел кадров» право включено.
- Флажок маршрута «Утверждать сразу»: заявка утверждается при подаче, шаги маршрута не действуют, пока флажок не снят. При первом открытии создаётся демо-маршрут «Больничный» — единственный для этого вида и утверждается сразу; чтобы больничный согласовывали, снимите флажок (шаг руководителя в нём уже есть). Признак — `kind_routes_ready` в `app.option`.
- В «Графике отсутствий» при установке и обновлении добавляются значения «Отгул» и «Больничный», если подходящих нет (`lists.field.update`: имеющиеся значения передаются обратно в `LIST`, новые — в `LIST_TEXT_VALUES`). «Отгул за свой счёт» отгулом не считается: ищется точное название.

## Гид

- Кнопка «Гид» в шапке запускает пошаговые подсказки (`public/assets/tour.js`): подсвечивает элемент и сама открывает нужную вкладку. Сценарий «Как пользоваться» — для всех, «Как настроить» — для тех, у кого есть право изменять «Доступ», «Маршруты», «Настройки» или «Остатки». Шаги по закрытым ролями вкладкам не показываются.
- При первом открытии приложения гид запускается сам один раз; отметка хранится в `BX24.userOption` (`tour_seen`), на сервер ничего не уходит.

## Мобильное приложение Битрикс24

Вёрстка адаптивная: на экране до 640 px (телефон, мобильное приложение Битрикс24) приложение перестраивается, шире — выглядит как раньше, десктоп от 1280 px без изменений и без горизонтальной прокрутки.

- В шаблоне есть `<meta name="viewport">`: без него встроенный браузер мобильного приложения масштабирует страницу как десктопную.
- Вкладки — лента с прокруткой, активная вкладка прокручивается в видимую часть.
- Календарь, масштаб «Месяц»: компактная сетка без имён и под ней список «Кто отсутствует» по дням; подряд идущие дни с одним и тем же составом сливаются в одну строку («9–15»). Обозначения свёрнуты. Нажатие на день открывает список отсутствующих и «Подать заявку с этой даты», нажатие на имя — карточку заявки. Квартал и год — по одному месяцу в ряд.
- «Мои заявки», «На согласовании», «На ознакомлении», остатки, лимиты отделов, шаги маршрутов, списки дашборда: строки таблиц показываются карточками «подпись — значение». Подписи берутся из заголовков столбцов, их проставляет `public/assets/mobile.js` при каждой перерисовке таблицы.
- Форма заявки, карточка заявки («Согласовать», причина и «Отклонить», «Отменить отсутствие», «Ознакомился»), настройки, маршруты, доступ — в одну колонку, поля и кнопки во всю ширину, шрифт в полях 16 px (иначе iOS приближает страницу при вводе).

Чтобы приложение открывалось в мобильном Битрикс24, в настройках локального приложения отметьте «Поддерживает BitrixMobile» (в карточке версии в Маркете — то же поле). По требованиям Маркета эту опцию включают только для полностью адаптивного приложения.
